# Руководство для AI-агентов

Этот документ описывает правила работы над проектом **BankCashOps**. Он
адресован AI-агентам и людям-разработчикам; следуйте ему при любых изменениях.

## Назначение проекта

Трёхуровневая система учёта кассовых операций банка:

- **Frontend** — React + TypeScript + Vite (SPA), общается с backend по REST.
- **Backend** — Django + Django REST Framework, аутентификация по JWT.
- **База данных** — PostgreSQL (единая для разработки и эксплуатации).

Проект развивается как **модульный монолит со строгими границами**: продукт
собирается из независимых модулей, каждый из которых содержит свои слои
frontend, backend и данных и публикует контракт. Основание и правила — в
`docs/adr/0001-modular-monolith.md` и `docs/modules.md`.

Текущее состояние: техническая библиотека `common` и доменный модуль `core`
(пользователи, аутентификация, роли) уже живут в `modules/`. Остальные модули
добавляются по мере развития.

## Языковые правила

| Что | Язык |
| --- | --- |
| Код: идентификаторы, комментарии, docstring | **английский** |
| Сообщения коммитов | **английский** |
| Документация `.md`, README, этот файл | **русский** |
| Тексты интерфейса (React) | **русский** |
| Строки, возвращаемые API клиенту | английский исходный текст, обёрнутый в `gettext_lazy` |

## Окружение разработки

Локальные Python и Node.js не требуются. Все операции выполняются в контейнерах
через Docker Compose из корня репозитория:

```bash
docker compose up -d                                   # запустить стек
docker compose exec backend python manage.py <команда> # команды Django
docker compose exec backend pytest                     # тесты
docker compose exec backend ruff check .               # линтер
docker compose exec frontend npm run build             # типы + сборка SPA
```

Перед запуском скопируйте `.env.example` в `.env` (значения по умолчанию годятся
для разработки).

## Работа с Git

- **Имя ветки изменения начинается с `feature/`**: `feature/<краткое-описание>`,
  например `feature/postgres-in-development`.
- **`main` защищена**: прямые коммиты запрещены, изменение вливается через
  отдельную ветку и pull request.
- Сообщения коммитов — на английском, в повелительном наклонении (см. таблицу
  «Языковые правила»).

Полный цикл (ветка → коммит → push → PR → merge) описан в `docs/development.md`,
раздел «Работа с Git и GitHub».

## Правила работы с кодом

1. **Не редактируйте существующие миграции.** Изменяйте модели и создавайте
   новые миграции командой `makemigrations` внутри контейнера.
2. **Миграции создаются только внутри контейнера**, чтобы совпадали версии
   зависимостей.
3. **Покрывайте новую логику тестами** (`modules/<модуль>/backend/tests/`).
4. **Соблюдайте стиль**: `ruff check .` и `black` (line-length 100) для backend.
5. **Не храните секреты в репозитории.** Всё, что зависит от окружения, читается
   из переменных окружения через `django-environ`.
6. **Переводы строк — LF.** Файлы из Windows должны сохраняться с LF
   (см. `.gitattributes` и `.editorconfig`); CRLF в `*.sh` ломает контейнер.
7. **Не расширяйте область изменения** без необходимости: правки минимальны и
   локализованы задачей.

## Модульная архитектура и границы

Модули общаются только через контракты. При работе над кодом соблюдайте
инварианты из `docs/modules.md`:

1. Модуль импортирует у соседа только его `contracts/`; чужие `models`, `views`,
   `services`, `serializers` и прямой доступ к чужим таблицам через ORM
   запрещены.
2. Данные принадлежат модулю: читает и пишет их только сам модуль.
3. Ссылка на сущность соседа хранится по стабильному идентификатору, а не как
   ORM-связь в чужую таблицу.
4. Согласованность между модулями — через доменные события (outbox), а не через
   общие транзакции. Синхронный вызов соседа допустим только для нетранзакционных
   запросов.
5. Контракты версионируются; ломающие изменения — только в новой мажорной версии
   модуля.

Состав поставки задаётся профилем заказчика (`profiles/`), параметры модуля —
его манифестом `module.yaml`. Адрес соседнего модуля не хардкодится: он
разрешается композицией по профилю.

## Как добавить новый backend-модуль

Модуль — вертикальный срез `modules/<name>/` со слоями `backend/`, `frontend/`,
`contracts/` и манифестом `module.yaml` (шаблон — `modules/_template/`). Полный
порядок описан в `docs/modules.md`, раздел «Как добавить модуль».

1. Создайте каталог `modules/<name>/backend/` — Django-приложение с `apps.py`,
   `models.py`, `serializers.py`, `views.py`, `urls.py`, `admin.py`, `migrations/`,
   `tests/`. В `AppConfig` задайте `name = "modules.<name>.backend"` и явный
   `label` (метка приложения, например `<name>`).
2. Зарегистрируйте приложение в `INSTALLED_APPS` (`config/settings.py`).
3. Подключите маршруты в `config/urls.py` внутри `api_patterns`.
4. Переиспользуйте общие блоки из `modules.common.backend` (`TimeStampedModel`,
   `StandardResultsSetPagination`, `IsAdminRole`).
5. Опишите публичный контракт в `modules/<name>/contracts/` и зарегистрируйте его
   реализацию в реестре (`modules.common.contracts.registry`) в `AppConfig.ready`.
6. Создайте миграции: `docker compose exec backend python manage.py makemigrations`.
7. Напишите тесты и покройте публичное поведение API и контракта.
8. Опишите модуль в `docs/api.md`, `module.yaml` и, при необходимости, в этом файле.

## Как добавить страницу во frontend

Frontend собран из хоста (`frontend/src/`) и фронтендов модулей
(`modules/<name>/frontend/`). Хост предоставляет общий SDK, layout и реестр
модулей; модуль владеет своими страницами, API-клиентами и манифестом.

1. Страница модуля — компонент в `modules/<name>/frontend/pages/`.
2. Вызовы API модуля — в `modules/<name>/frontend/api/`.
3. Общие блоки (HTTP-клиент, ошибки, типы identity, роли, layout) — из хостового
   SDK по псевдониму `@app/*`; свои файлы — относительно; импорт из другого
   модуля запрещён.
4. Маршрут и пункт навигации объявляются в манифесте модуля
   `modules/<name>/frontend/index.tsx` (контракт `FrontendModule`).
5. Включите модуль в композицию: `frontend/src/registry/index.ts`.
6. Хостовые страницы (панель, профиль, вход, 404) остаются в `frontend/src/`.
7. Тексты интерфейса — на русском.

## Ключевые точки входа

- Архитектурные решения: `docs/adr/`
- Правила модулей и контрактов: `docs/modules.md`
- Настройки: `backend/config/settings.py`
- Корневые URL: `backend/config/urls.py`
- Модель пользователя: `modules/core/backend/models.py`
- API пользователей: `modules/core/backend/views.py`
- HTTP-клиент SPA: `frontend/src/api/client.ts`
- Контекст аутентификации: `frontend/src/auth/AuthContext.tsx`
- Реестр модулей SPA: `frontend/src/registry/index.ts`
- Контракт фронтенд-модуля: `frontend/src/registry/contract.ts`

## Проверка перед завершением задачи

```bash
docker compose exec backend ruff check .
docker compose exec backend pytest
docker compose exec frontend npm run build
```

Все три команды должны завершаться успешно.
