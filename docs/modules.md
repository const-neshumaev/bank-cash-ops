# Модули

Этот документ описывает, как устроен модуль BankCashOps, как модули общаются
между собой, каким правилам подчиняются границы и как из модулей собирается
поставка конкретному заказчику.

Основание — решение `docs/adr/0001-modular-monolith.md`.

## Что такое модуль

Модуль — **вертикальный срез функциональности**, независимо развиваемая часть
продукта. Каждый модуль:

- отвечает за свою предметную область и **владеет своими данными**;
- содержит собственные слои **frontend**, **backend** и **данных**;
- публикует **контракт** — единственный способ, которым им пользуются другие;
- описывает себя **манифестом** `module.yaml`.

Примеры модулей: `core` (ядро), `operations` (кассовые операции), `reports`
(отчётность), `audit` (аудит).

`common` — это **не модуль**, а техническая библиотека (базовые модели,
пагинация, примитивы контрактов). Она не имеет предметной области и не
поставляется отдельно.

## Структура модуля

```text
modules/<name>/
├── backend/            # Django-приложение (модели, миграции, views, services)
├── frontend/           # страницы, API-клиенты и типы SPA
├── contracts/          # публичный интерфейс: DTO, сервисные интерфейсы, события
└── module.yaml         # манифест модуля
```

## Инварианты (правила границ)

Эти правила — суть «высокой связности внутри, низкой связности снаружи». Их
обязательно соблюдать и проверять в ревью.

1. **Зависимости только через контракт.** Модуль импортирует у соседа
   исключительно его `contracts/`. Запрещено импортировать чужие
   `models`, `views`, `services`, `serializers` и обращаться к чужим таблицам
   через ORM.
2. **Данные принадлежат модулю.** Только модуль читает и пишет свои таблицы.
   Другой модуль работает с ними через сервис контракта.
3. **Межмодульные ссылки — по идентификатору.** Ссылка на сущность соседа
   хранится как стабильный идентификатор, раскрытый контрактом (`user_id`,
   `cash_desk_id`), а не как ORM-связь в чужую таблицу.
4. **Согласованность — через события, не через общие транзакции.** То, что
   должно произойти в другом модуле, публикуется доменным событием (outbox).
   Синхронные вызовы соседа допустимы только для нетранзакционных запросов.
5. **Контракт версионируется.** Ломающие изменения контракта — только в новой
   мажорной версии модуля.
6. **Одна точка входа в каждый модуль.** Внешний код зависит от абстракции
   (интерфейса), а не от реализации, чтобы способ вызова можно было сменить
   конфигурацией.

## Контракты

Контракт — это публичный «фасад» модуля. Технически — Python-пакет `contracts/`
с тремя видами сущностей.

### DTO

Неизменяемые типы для передачи данных через границу. Никаких ORM-моделей наружу.

```python
# modules/core/contracts/dto.py
from dataclasses import dataclass


@dataclass(frozen=True)
class UserDTO:
    id: int
    email: str
    role: str
    is_active: bool
```

### Сервисный интерфейс

Абстракция (Python `Protocol` или ABC), описывающая, что модуль умеет. Реализация
живёт внутри модуля и наружу не экспортируется.

```python
# modules/core/contracts/services.py
from typing import Protocol

from .dto import UserDTO


class UserDirectory(Protocol):
    def get_user(self, user_id: int) -> UserDTO | None: ...

    def is_allowed(self, user_id: int, permission: str) -> bool: ...
```

### Реестр сервисов

Потребитель получает реализацию через реестр, а не через прямой импорт. Реестр
разрешает in-process реализацию или сетевой клиент по конфигурации — именно
здесь «адрес другого модуля» превращается в конкретный объект.

```python
# внутри модуля operations
from modules.common.contracts import registry
from modules.core.contracts.services import UserDirectory

users: UserDirectory = registry.get("core.users")
if not users.is_allowed(current_user_id, "operations.create"):
    ...
```

### Доменные события (outbox)

Для распространения изменений между модулями используется шаблон **outbox**:
модуль пишет событие в свою таблицу исходящих событий в той же транзакции, что и
бизнес-изменение, а диспетчер доставляет его подписчикам. Это даёт согласованность
без распределённых транзакций и без синхронной зависимости от соседа.

```python
# внутри транзакции модуля operations
outbox.publish(
    topic="operations.cash_operation.created",
    payload={"operation_id": op.id, "amount": str(op.amount)},
)
```

Подписчик (`reports`) получает событие и обновляет свой read-model.

## Владение данными и БД

Одна СУБД, но **каждый модуль владеет своим набором таблиц**.

- **Целевое состояние:** каждому модулю соответствует отдельная схема
  PostgreSQL (`core`, `operations`, `reports`). Схема даёт физическое разделение
  прав, резервного копирования и изоляцию.
- **Текущий шаг:** пространства имён таблиц по модулю (`core_*`, `operations_*`).
  Это совместимо с SQLite в разработке и не создаёт расхождения «разработка vs
  эксплуатация».

Причина поэтапности: у Django нет встроенной поддержки схем «из коробки», а SQLite
(разработка по умолчанию) схем не поддерживает вовсе. Так как контракт скрывает
ORM, перевод на реальные схемы не потребует изменений в коде модулей — только в
слое доступа к данным и конфигурации.

Межмодульных ORM-связей (`ForeignKey` в чужую таблицу) быть не должно — см.
инвариант 3.

## Frontend модуля

Frontend собран из **хоста** (`frontend/src/`) и **фронтендов модулей**
(`modules/<name>/frontend/`). Композиция выполняется на этапе сборки; микро-
фронтенды (runtime-федерация) не используются.

Разделение ответственности:

- **Хост** предоставляет общий SDK и каркас приложения: HTTP-клиент и обработку
  ошибок, сессию и аутентификацию (вход, профиль, защита маршрутов), типы
  identity и роли, layout, панель, 404, а также реестр модулей.
- **Модуль** владеет своей фичей: страницами, API-клиентами и манифестом.

Правила:

1. Модуль импортирует общий SDK хоста по псевдониму `@app/*`; свои файлы — по
   относительным путям. Импорт из другого модуля запрещён.
2. Модуль объявляет маршруты и пункты навигации в манифесте
   `modules/<name>/frontend/index.tsx`, реализуя контракт `FrontendModule`
   (`frontend/src/registry/contract.ts`).
3. Хост собирает маршруты и навигацию из включённых модулей и добавляет свои
   страницы.

Контракт фронтенд-модуля:

```ts
export interface FrontendModule {
  id: string
  title: string
  routes: ModuleRoute[] // { path, element, access?: 'protected' | 'admin' }
  nav?: ModuleNavItem[] // { label, to, icon?, adminOnly? }
}
```

Пример манифеста:

```tsx
export const coreFrontend: FrontendModule = {
  id: 'core',
  title: 'Ядро',
  routes: [{ path: 'users', element: <UsersPage />, access: 'admin' }],
  nav: [
    { label: 'Пользователи', to: '/users', icon: <IconUsers size={18} />, adminOnly: true },
  ],
}
```

Точка композиции — `frontend/src/registry/index.ts`: список включённых модулей
(аналог `INSTALLED_APPS` на backend). Сборка экспонирует фронтенды модулей внутри
корня фронтенда как `./modules` (bind mount в разработке, копирование в
эксплуатации), чтобы разрешение модулей находило общий `node_modules`.

## Манифест модуля

`modules/<name>/module.yaml` описывает модуль: его версию, зависимости,
публичный контракт и параметры конфигурации.

```yaml
name: operations
title: Кассовые операции
version: 0.1.0
description: Приход и расход наличных, кассовые смены.

# Зависимости от других модулей.
dependencies:
  - name: core
    version: ">=0.1,<1"
    access: inprocess        # inprocess | http

# Что модуль публикует наружу.
provides:
  contracts: modules.operations.contracts   # python-путь пакета контрактов
  api_base: /api/operations/                 # префикс REST
  frontend_routes: true                      # модуль добавляет маршруты в SPA

# Ключи конфигурации, которые модуль читает из окружения.
config:
  - name: BCO_OPERATIONS_MAX_AMOUNT
    description: Максимальная сумма одной операции.
    default: "1000000"
```

Обязательные поля: `name`, `version`. Остальные — по необходимости.

Правила:

- `name` уникален в пределах поставки и совпадает с именем каталога.
- `version` — semver; для независимых релизов версия меняется независимо от
  остальных модулей.
- `dependencies[].access` (`inprocess` | `http`) по умолчанию берётся из профиля
  заказчика, если он там задан.

## Профиль заказчика

`profiles/<customer>.yaml` — комплектация поставки: какие модули включены и как
они находят друг друга. Это единственное место, где задаётся «адрес» модуля.

```yaml
product: bank-cash-ops
version: 0.1.0

modules:
  - name: core
    version: 0.1.0

  - name: operations
    version: 0.1.0
    connections:
      core:
        access: inprocess
        # url: http://core:8000    # обязателен при access: http

  - name: reports
    version: 0.1.0
    connections:
      core: { access: inprocess }
      operations: { access: http, url: "http://operations:8000" }
```

- Список `modules` определяет состав сборки.
- `connections` переопределяет способ обращения к модулю, если он отличается от
  указанного в манифесте. Пока все модули в одном процессе — `access: inprocess`.
- `url` нужен только при `access: http` и берётся из окружения на этапе сборки.

Готовый пример — `profiles/example.yaml`.

## Композиция поставки

Слой композиции читает профиль и подготавливает сборку:

- **backend:** формирует `INSTALLED_APPS` и подключает маршруты только включённых
  модулей.
- **frontend:** подключает страницы и пункты навигации из включённых модулей
  (композиция на этапе сборки; микрофронтенды не используются).
- **инфраструктура:** определяет состав контейнеров и их конфигурацию.

Никакой модуль не хардкодит расположение соседа — это делает композиция по
профилю. Пока композиция выполняется на этапе сборки образа под заказчика; при
необходимости её можно вынести в отдельный генератор/скрипт.

## Нейминг

Регистр зависит от того, где имя используется:

| Сущность | Схема | Пример |
| --- | --- | --- |
| Каталог модуля, repo, Docker image | kebab-case с префиксом продукта | `bank-cash-ops-operations` |
| Тег образа | semver | `bank-cash-ops-operations:0.1.0` |
| Python-пакет | snake_case | `modules.operations` |
| npm-пакет | scope | `@bank-cash-ops/operations` |
| Схема БД (целевая) | snake_case | `operations` |
| Env-ключи | SCREAMING_SNAKE с префиксом | `BCO_OPERATIONS_*` |
| Префикс REST API | префикс модуля | `/api/operations/...` |

Префикс продукта — `bank-cash-ops` (для артефактов) и `BCO` (для переменных
окружения).

## Как добавить модуль

1. Создайте каталог `modules/<name>/` со слоями `backend/`, `frontend/`,
   `contracts/` (см. шаблон `modules/_template/`).
2. Опишите модуль в `module.yaml`.
3. Реализуйте backend по правилам из этого документа; публичное поведение
   покройте тестами.
4. Опишите контракт в `contracts/` (DTO, сервисные интерфейсы, события).
5. Опишите REST API модуля в `docs/api.md`.
6. Включите модуль в профиль заказчика (`profiles/`) и зарегистрируйте в
   композиции: backend — `INSTALLED_APPS` и URL; frontend — манифест
   `modules/<name>/frontend/index.tsx` и список `frontend/src/registry/index.ts`.
7. Если модуль зависит от других — укажите их в `dependencies` и используйте
   только их контракты.
