# ADR 0011. Внешние операции: бронь наличных, идемпотентность и интеграционные точки

- **Статус:** Принято
- **Дата:** 2026-10-14
- **Контекст задачи:** операции, обращающиеся к внешним подсистемам банка по REST.

## Контекст

Часть операций конкретного банка (снятие/пополнение вклада, погашение кредита и
т.п.) требует обращения к внешним подсистемам банка по REST. Такие операции
реализуются разработчиком под API соответствующего банка — как расширения
(ADR 0006). Адрес хоста задаёт администратор в конфигурации.

Ключевая проблема: сетевой вызов нельзя выполнить внутри транзакции БД, но учёт
наличных должен оставаться согласованным и не допускать двойной выдачи денег.

## Решение

1. **Тип операции может быть внешним.** Обработчик объявляет интеграционную точку.
2. **Интеграционная точка (`IntegrationEndpoint`) — данные в `operations`:**
   код, базовый URL, ссылка на секрет, таймауты, повторы. Секреты **не хранятся
   в БД и репозитории**: хранится ссылка на переменную окружения / secret
   manager (правило `AGENTS.md`). Адрес задаёт администратор.
3. **Статусная модель (сага).** Операция проходит состояния:
   `draft → validated → external_pending → posted | failed`; из `posted` возможен
   переход в `reversed`. Сетевой вызов — на шаге `external_pending`, вне
   транзакции БД.
4. **Бронь наличных.** Перед внешним вызовом наличные **резервируются** (hold) на
   регистре `cash`, чтобы не выдать их дважды параллельно; после успеха —
   проведение по факту, при ошибке — снятие брони. Бронь уменьшает **доступный**
   остаток, но не сам остаток.
5. **Идемпотентность сквозная.** Идемпотентный ключ передаётся во внешний API и
   хранится с операцией — для безопасных повторов при ретраях.
6. **Внешняя ссылка сохраняется.** Идентификатор операции во внешней системе
   хранится с нашей операцией для сверки и разбора.
7. **Обработчик внешней операции** — код в модуле-расширении, реализованный под
   конкретный API банка (ADR 0006).

## Обоснование

Бронь наличных — самый надёжный способ не выдать деньги, пока внешний вызов в
процессе: доступный остаток сразу уменьшается, а проведение завершает операцию
только после подтверждения внешней системы. Статусная модель делает прозрачным
состояние «операция в процессе/ошиблась», а идемпотентный ключ защищает от
дублей при повторах — всё это критично для банковского учёта.

## Последствия

Положительные:

- Нет двойной выдачи наличных при параллельных внешних вызовах.
- Состояние внешней операции наблюдаемо и разбираемо.
- Секреты не попадают в БД и репозиторий.

Отрицательные и риски:

- Бронь добавляет состояние к регистру `cash` (доступный остаток ≠ остаток).
- Требуется разбор `failed` (ручной или автоматический) — операционный процесс.
- Возможны «зависшие» брони при сбоях — нужен механизм истечения/снятия.

## Отложенные решения

- **Конкретная механика брони** (истечение, снятие, перевод в проведение),
  **ретраи и компенсации**, **ручной разбор `failed`** — при реализации внешних
  операций (не первый этап).
