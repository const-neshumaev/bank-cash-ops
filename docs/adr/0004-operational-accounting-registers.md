# ADR 0004. Операционный учёт: регистры накопления и односторонние проводки

- **Статус:** Принято
- **Дата:** 2026-10-14
- **Контекст задачи:** модель учёта кассовых операций в модуле `operations`.

## Контекст

Продукт ведёт учёт кассовых операций банка. Нужно решить, строить ли учёт как
полноценную бухгалтерию (двойная запись с планом счетов) или ограничиться учётом
движения наличных.

Дополнительная сложность: у разных операций разное число сумм в разных валютах.
Подкрепление кассы — одна сумма (например 500 USD); продажа валюты — принято
500 BYN, выдано 125 USD, возможна отдельная сумма дробной покупки. Значит, одной
«суммы операции» недостаточно.

## Решение

1. **План счетов и двойная запись не ведутся.** Учёт строится на **регистрах
   накопления**: регистр = код + набор измерений + ресурсы. **Проводка**
   (movement) = регистр + значения измерений + **знаковая** сумма.
2. Отказ от двойной записи не означает отказа от модели: для каждого типа
   операции задаётся **локальный инвариант** (например, сохранение суммы при
   обмене по курсу), и его соблюдение — ответственность типа операции.
3. **Операция — неизменяемый документ**: тип, касса, смена, кассир, клиент
   (снимок), статус, номер, время. Суммы хранятся **строками** операции
   (слот → валюта → сумма, при необходимости курс). Проводки движок строит из
   строк по правилу типа операции.
4. **Журнал неизменяем.** Исправление оформляется **сторно** — обратными
   проводками со ссылкой на исходную операцию. Редактирование проведённой
   операции запрещено.
5. **Стартовые регистры:** `cash` (остаток наличных: измерения «касса» +
   «валюта») и `turnover` (обороты: «касса» + «валюта» + «вид операции»). Набор
   регистров расширяется по мере надобности (расчёты с клиентами, комиссии,
   курсовые разницы).
6. **Экспорт в АСУ банка — вне домена.** Операции публикуются доменными
   событиями (см. ADR 0009) и/или выгружаются для импорта в систему
   бухгалтерского учёта банка; сверка с бухгалтерией — забота внешней системы.

## Обоснование

Для кассового модуля ценность — точный учёт **наличных денег** (сколько каких
денег в кассе), а не ведение главной книги. Полноценный план счетов дублировал бы
функцию АСУ банка, потребовал бы её методологии и увеличил стоимость изменения
без пользы для учёта наличных. Регистры накопления дают необходимую модель
(измерения + ресурсы), естественно вмещают разное число сумм операции и остаются
расширяемыми.

## Последствия

Положительные:

- Модель прямо отражает предметную область — движение наличных по кассам и
  валютам.
- Разное число сумм и валют в операции выражается строками и проводками без
  «универсальной» суммы, теряющей смысл.
- Неизменяемый журнал + сторно дают аудируемость.

Отрицательные и риски:

- Нет готового соответствия плану счетов — потребуется слой сопоставления при
  экспорте в АСУ банка.
- Локальные инварианты типов операций надо задавать явно и покрывать тестами.
