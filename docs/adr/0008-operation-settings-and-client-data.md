# ADR 0008. Настройки операций и данные клиента

- **Статус:** Принято
- **Дата:** 2026-10-14
- **Контекст задачи:** настраиваемость операций и работа с данными клиента.

## Контекст

Операции отличаются по требованиям к данным клиента: одним нужны данные клиента,
другим — нет; после некоторого порога по сумме требуется запрашивать паспортные
данные. Эти настройки — сквозные для всего банка. Кроме того, разным кассам
разных отделений нужен свой список доступных операций.

## Решение

1. **Настройки на уровне типа операции:** признак «требуются данные клиента»,
   порог суммы, после которого обязателен документ, и другие флаги задаются в
   метаданных типа операции.
2. **Банковские значения по умолчанию — singleton в БД.** Настройки
   (`OperationsSettings`): базовая валюта банка, общий порог суммы, общий признак
   обязательности клиента. Редактируются администратором (право
   `operations.config.manage`). Значения по умолчанию для первичного заполнения
   берутся из `module.yaml` / переменных окружения (`BCO_OPERATIONS_*`), но
   **редактируемая часть хранится в БД**, а не в `settings.py`.
3. **Список операций, доступных на кассе,** хранит `operations`: таблица
   «касса → разрешённый тип операции» (ссылки `cash_desk_id` и код типа).
   Настройка — по праву `operations.config.manage`. Валюты кассы — в `core`
   (см. ADR 0007).
4. **Данные клиента — снимок в операции.** Полноценного учёта клиентов (CRM) нет
   и не планируется в `operations`. Когда операция требует данных клиента, в
   операции сохраняется **снимок** (ФИО, документ и т.п.) — для аудита и экспорта.
   Отдельный модуль `clients` возможен в будущем, но не является частью
   `operations`.
5. **Порог считается в базовой валюте банка.** Суммы в других валютах
   пересчитываются по курсу-снимку (см. ADR 0007).

## Обоснование

Сквозные настройки банка (порог, обязательность клиента) должны меняться
администратором без пересборки — отсюда singleton в БД. Список операций на кассе
и валюты отражают разную комплектацию рабочих мест; хранение доступных операций
в `operations` (владельце типов) и валют в `core` (владельце кассы) сохраняет
границы модулей. Снимок клиента в операции — минимальный способ обеспечить
аудит без построения CRM.

## Последствия

Положительные:

- Порог и обязательность клиента меняются без изменения кода и пересборки.
- Комплектация кассы (операции, валюты) настраивается независимо.
- Нет избыточного модуля клиентов на раннем этапе.

Отрицательные и риски:

- Данные клиента дублируются снимками в операциях (осознанно).
- `OperationsSettings` — singleton; нужна аккуратная работа с правами и
  валидацией.

## Отложенные решения

- **Модуль `clients`** (учёт клиентов) — при появлении реальной потребности.
