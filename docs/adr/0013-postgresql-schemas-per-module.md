# ADR 0013. Схемы PostgreSQL по модулю

- **Статус:** Принято
- **Дата:** 2026-10-15
- **Контекст задачи:** перевод «пространств имён таблиц» в реальные схемы БД —
  немедленный шаг, отложенный в `docs/adr/0001-modular-monolith.md`.

## Контекст

ADR 0001 объявил целевым состоянием **отдельную схему PostgreSQL на модуль** и
отложил переход на неё отдельным решением. К этому моменту подготовка завершена:

- разработка, тесты и эксплуатация уже используют PostgreSQL
  (`docs/adr/0002-postgresql-in-development.md`);
- таблицы модулей именуются по метке приложения (`core_*`, `operations_*`,
  `common_*`) — это и было «текущим шагом» из `docs/modules.md`;
- межмодульных ORM-связей нет: ссылки хранятся по идентификаторам
  (`cash_desk_id`), поэтому почти все внешние ключи замкнуты внутри одного модуля;
- `GenericForeignKey` и `contenttypes` в модулях не используются.

Django не поддерживает схемы «из коробки», поэтому решение требует явного
приёма квалификации таблиц и автоматического создания схем.

## Решение

- **Схема на модуль.** Каждый доменный модуль владеет схемой PostgreSQL с именем,
  равным метке приложения: `core`, `operations`. Техническая библиотека `common`
  владеет схемой `common` (в ней живёт таблица outbox). Модуль без моделей (например
  `operations_standard`) схемы не получает.
- **Имя таблицы внутри схемы не меняется** (`core_user`, `operations_operation`).
  Таблицы не переименовываются, поэтому имена индексов и ограничений, которые
  Django выводит из имени таблицы, остаются прежними — переезд не создаёт «скрытых»
  расхождений между моделями и физической БД.
- **Квалификация — в `Meta.db_table`** через хелпер
  `modules.common.backend.schemas.qualified_table`; авто-создаваемые таблицы
  «многие-ко-многим» наследуют схему родителя автоматически. Системная проверка
  `modules.E001` (`modules/common/backend/checks.py`) не даёт забыть
  квалификацию: она срабатывает в `manage.py check`, `runserver` и CI-шаге
  `makemigrations --check`.
- **Схемы создаются автоматически перед миграциями** — обработчик сигнала
  `pre_migrate` в `modules/common/backend/schemas.py` выполняет
  `CREATE SCHEMA IF NOT EXISTS`. Это покрывает свежую БД, стек разработки и
  тестовую БД без ручных шагов и без изменения уже применённых миграций.
- **Перенос существующих таблиц** выполняется разовыми миграциями
  `SeparateDatabaseAndState`: состояние меняется через `AlterModelTable`, а
  физический перенос — `ALTER TABLE ... SET SCHEMA` в `RunSQL`. Причина разделения:
  schema editor Django умеет переименовывать таблицу, но не перемещать её между
  схемами.
- **Ядро Django остаётся в `public`:** `contenttypes`, `auth`, `admin`, `sessions`,
  `token_blacklist`, `django_migrations`.
- **SQLite-запасной вариант удалён**, `DATABASE_URL` стал обязательным; CI поднимает
  сервис PostgreSQL вместо временного SQLite-файла.

## Обоснование

Переезд дешёв именно сейчас: межмодульных ORM-связей ещё нет, а стоимость
переезда растёт с каждой новой таблицей. Схемы дают административную изоляцию
(права на уровне схемы, бэкап и дамп по модулю, явное владение данными) и готовый
шов для будущего выноса модуля в отдельную БД — дамп схемы совпадает с границей
модуля. Согласованность при этом сохраняется: это по-прежнему одна СУБД и одна
транзакция (основание — ADR 0001).

## Последствия

Положительные:

- Данные каждого модуля физически обособлены внутри общей СУБД.
- Права выдаются на схему (`GRANT ... ON SCHEMA core`), резервная копия и выгрузка
  делаются по схеме (`pg_dump -n core`).
- Владение данными закреплено физически, а не только соглашением.
- Готовый путь выноса модуля: схему можно перенести в отдельную БД.

Отрицательные и риски:

- **`core` не изолирована полностью.** Из-за `AUTH_USER_MODEL` и наследования
  `AbstractUser` остаются кросс-схемные внешние ключи между `public` и `core`:
  `django_admin_log.user` и `token_blacklist_outstandingtoken.user` ссылаются на
  `core.user`, а `core.user_groups` и `core.user_user_permissions` — на
  `auth.group` / `auth.permission`. Схема — **административная** граница, а не
  физический «забор» от ядра Django.
- **Квалификация `db_table` — соглашение, а не возможность Django.** При добавлении
  модели нужно не забыть задать `db_table` через хелпер. От «тихого» пропуска
  страхует системная проверка `modules.E001`, но `migrate` её не прогоняет — в CI
  квалификацию проверяет шаг `makemigrations --check`, а на практике — `manage.py
  check`.
- Схему создаёт `pre_migrate`, поэтому миграции запускаются только через
  `migrate` (в том числе из создания тестовой БД); произвольный DDL вне `migrate`
  схему не создаст.
