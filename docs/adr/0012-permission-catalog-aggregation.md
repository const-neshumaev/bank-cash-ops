# ADR 0012. Агрегация каталога прав из модулей

- **Статус:** Принято
- **Дата:** 2026-10-14
- **Контекст задачи:** доступ к функциям модулей (например, рабочему месту
  кассовых операций).

## Контекст

ADR 0003 зафиксировал, что каталог прав — это код в
`modules/core/backend/permission_codes.py`, а роли ссылаются на коды из каталога.
С появлением модуля `operations` понадобились его права (`operations.*`). Хранить
коды соседа в файле `core` — нарушение границ модулей; и наоборот, дать роли
недоступные коды нельзя, иначе функции модуля никто не сможет получить.

## Решение

Каждый модуль объявляет **свой** каталог прав (модуль — владелец своих кодов) и
регистрирует его в общем реестре `modules.common.backend.permissions_catalog` в
`AppConfig.ready()`. Каталоги **агрегируются**: эндпоинт `/api/permissions/` и
валидация роли читают объединение. Администратор назначает новые коды ролям через
интерфейс ролей.

## Обоснование

Агрегация — тот же приём, что и реестр сервисов контрактов
(`modules.common.contracts.registry`): он скрывает расположение кодов и сохраняет
границы. `core` остаётся владельцем своих кодов, `operations` — своих; ни один
модуль не знает коды соседа.

## Последствия

Положительные:

- Коды нового модуля доступны ролям без правки `core`.
- Границы модулей соблюдены; каждый модуль — владелец своего каталога.

Отрицательные и риски:

- Коды становятся известны только после `AppConfig.ready()` (порядок — по
  `INSTALLED_APPS`).
- Назначение прав ролям — ручное действие администратора; автоматического grant
  при поставке нет.

## Отложенные решения

- **Автоматическое назначение прав системным ролям** при поставке (чтобы кассир
  получал права `operations.*` из коробки).
