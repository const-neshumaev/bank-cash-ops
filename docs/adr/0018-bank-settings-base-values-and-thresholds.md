# ADR 0018. Настройки банка, базовые величины и пороги типов операций

- **Статус:** Принято
- **Дата:** 2026-10-20
- **Контекст задачи:** глобальные настройки банка, справочник базовых величин и
  настраиваемые пороги запроса данных клиента.

## Контекст

Глобальные константы банка (национальная валюта) и справочник базовых величин
нужны нескольким модулям. Порог, после которого операция требует данные клиента,
зависит от типа операции и может измеряться по-разному: в базовых величинах или в
конкретной валюте. Настройки меняются администратором, поэтому изменения нужно
объяснять задним числом — с датой, временем и пользователем.

Прежняя модель (`OperationsSettings` и поля `OperationType.requires_client` /
`client_id_threshold`) не покрывала разные способы задания порога, дублировала
базовую валюту и затиралась синхронизацией объявлений при каждом старте.

## Решение

1. **Настройки банка остаются в `core.BankSettings`.** `base_currency` —
   единственный источник национальной валюты; `OperationsSettings` удаляется.
   Чтение настроек публичное, изменение — по праву `core.bank_settings.manage`.
   Смена валюты запрещена, пока есть курсы или базовые величины в другой валюте.
2. **Базовые величины — сущность `core.BaseValue`.** Поля: `effective_from`
   (уникальная дата), `amount`, `currency_code` (снимок валюты). Действует
   запись с наибольшей `effective_from` не позже даты операции. Будущие записи
   редактируются и удаляются, вступившие в силу — нет (append-only).
3. **Политика данных клиента задаётся на типе операции:**
   `never` / `always` / `threshold`. При `threshold` обязательны тип порога и его
   значение.
4. **Способы задания порога — реестр в коде.** Первые реализации:
   `base_value` (количество базовых величин) и `currency` (сумма в валюте).
   Новый способ добавляется кодом, а не данными; UI получает список из API.
   Проверка порога при проведении — отдельная итерация.
5. **История настроек типа — append-only.** `OperationTypeSettingsChange` хранит
   дату, пользователя (id + снимок email) и значения «до/после» изменённых полей.
   Пишется из REST API и Django admin; создание типа и синхронизация объявлений
   в историю не попадают.
6. **Синхронизация не управляет настройками.** `sync_operation_types` обновляет
   декларативные поля, а политику, порог и активность задаёт только при создании.
7. **Права:** `core.bank_settings.manage`, `core.base_values.view/manage`,
   `operations.types.manage`. Чтение базовых величин выдаётся всем системным
   ролям, изменение — администратору. История доступна по `operations.view`.

## Обоснование

Глобальные константы принадлежат ядру, а не движку операций: ими пользуются
курсы, пороги и отчётность. Разные способы порога нельзя выразить одним числом,
поэтому тип порога — стабильный код с параметрами. История в виде «до/после»
показывает, почему операция требовала или не требовала данные клиента в прошлом.
Запрет менять вступившие в силу базовые величины сохраняет смысл исторических
расчётов.

## Последствия

Положительные:

- Базовая валюта хранится в одном месте.
- Порог настраивается администратором без пересборки и без правки деклараций.
- Изменения настроек объяснимы задним числом.
- Новый способ порога добавляется без миграции данных.

Отрицательные и риски:

- Декларации типов не могут обновить уже настроенные администратором поля;
  изменение значения по умолчанию действует только на новые типы.
- Проверка порога пока не выполняется в движке — это следующая итерация.
