# ADR 0002. PostgreSQL в разработке и эксплуатации

- **Статус:** Принято
- **Дата:** 2026-10-12
- **Контекст задачи:** паритет окружений разработки и эксплуатации.

## Контекст

Ранее разработка велась на SQLite, а эксплуатация — на PostgreSQL; СУБД
выбиралась переменной `DATABASE_URL`. SQLite удобен для быстрого старта, но его
поведение расходится с PostgreSQL именно там, где для банковского учёта кассовых
операций важна надёжность:

- `select_for_update()` на SQLite не выполняет блокировку строк, поэтому
  конкурентный доступ к остаткам и сменам нельзя достоверно протестировать.
- `DecimalField` не обеспечивает строгую точность и ограничение разрядности —
  ошибки округления денежных сумм проявляются только в эксплуатации.
- Частичные и условные ограничения целостности, типы `django.contrib.postgres`
  (JSONB, массивы, диапазоны), `CREATE INDEX CONCURRENTLY` и различия коллаций на
  SQLite либо недоступны, либо ведут себя иначе.

## Решение

PostgreSQL 16 — единая СУБД для разработки, тестов и эксплуатации. Стек
разработки (`docker-compose.yml`) поднимает контейнер `db` с PostgreSQL, и backend
подключается к нему через `DATABASE_URL`. Возврат к SQLite в рабочем процессе
разработки не предполагается.

## Обоснование

Паритет dev/prod убирает класс дефектов «работает локально — падает в
эксплуатации»: миграции, ограничения БД, точность денежных полей и блокировки
проверяются на той же СУБД, что и в продакшене. Домен — транзакционный учёт
кассовых операций, где согласованность и точность критичны.

## Последствия

Положительные:

- Одинаковая СУБД во всех окружениях.
- Доступны специфичные для PostgreSQL типы, индексы и блокировки строк.
- Тесты выявляют расхождения с эксплуатацией раньше.

Отрицательные и риски:

- Больший расход ресурсов и времени на старт по сравнению с SQLite.
- Автотесты в CI потребуют сервиса PostgreSQL (вводится отдельным изменением).

## Запасной вариант SQLite (удалён)

`backend/config/settings.py` ранее сохранял запасной вариант на SQLite, когда
`DATABASE_URL` не задан. Он был нужен только как временный bootstrap для проверок,
которые ещё не были подняты на PostgreSQL (задание `backend` в CI), и **не** являлся
базой разработки. Запасной вариант **удалён**: `DATABASE_URL` стал обязательным, а CI
поднимает сервис PostgreSQL (см. `docs/adr/0013-postgresql-schemas-per-module.md`).
