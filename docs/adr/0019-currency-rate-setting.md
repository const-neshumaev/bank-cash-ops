# ADR 0019. Установка курсов валют: области, действие и версии

- **Статус:** Принято
- **Дата:** 2026-10-21
- **Контекст задачи:** ручная установка курсов, журнал и текущие курсы, права на
  уровни банка/отделения/кассы.

## Контекст

`core.CurrencyRate` умел хранить курс только для банка или кассы и не учитывал
признаки типа курса. Требуется:

- задавать курсы на трёх уровнях: банк, отделение, касса;
- разрешать наследование и отсекать вышестоящие уровни флагом «работает по
  индивидуальным курсам»;
- различать «один курс на календарный день» и «курс с момента установки»;
- требовать курс на дату операции для ежедневных типов;
- вести журнал всех установок и показывать действующие курсы;
- разграничить права администратора, заведующего отделением и кассира.

## Решение

1. **Область курса — одно из трёх значений.** `CurrencyRate.branch` и
   `CurrencyRate.cash_desk` не задаются одновременно: оба пусты — банк, задан
   `branch` — отделение, задан `cash_desk` — касса. Курс Нацбанка допускается
   только на уровне банка.
2. **Флаги `uses_individual_rates`** добавляются в `Branch` и `CashDesk` и
   отключают вышестоящие уровни. Порядок разрешения: касса → её отделение →
   родительские отделения → банк. Курс родительского отделения наследуется
   дочерними, пока более близкое отделение не задаст свой.
3. **Тип курса получает два признака.** `validity` (`calendar_day` /
   `since_set`) определяет форму хранения; `daily_required` — обязательность
   курса на дату операции. По умолчанию для `official`:
   `calendar_day` + `daily_required`; для остальных принципов: `since_set` без
   ежедневного требования.
4. **Хранение.** Для `calendar_day` заполняется `effective_date`, а
   `effective_from` нормализуется на начало локального дня; уникальность — по
   `(currency, base_currency, rate_type, branch, cash_desk, effective_date)` среди
   действующих версий. Для `since_set` заполняется только `effective_from`;
   уникальность — по времени среди действующих версий.
5. **Версии.** Исправление `calendar_day`-курса создаёт новую запись, прежняя
   помечается `superseded_at`; журнал сохраняет историю. Одиночный `POST` на
   занятую дату возвращает ошибку, bulk-сохранение работает как upsert.
6. **Журнал и текущие курсы.** Журнал — все записи, включая заменённые; текущие
   курсы — действующие версии на момент запроса. Банковские курсы видны всем с
   правом просмотра, курсы отделений и касс — в пределах доступных отделений.
7. **Права** — отдельные коды: `core.currency_rates.view`,
   `.manage`, `.manage.branch`, `.manage.cash_desk`, `.manage.official`.
   Администратор получает все; заведующий — просмотр и курсы своих отделений;
   кассир — просмотр и курсы кассы открытой смены; специалист — просмотр.
8. **Запрет смены `validity`** у типа, у которого уже есть курсы. Проверка
   выполняется через callback-контракт `RateTypeUsageGuard`: `references` не
   обращается к таблицам `core`, а реализацию предоставляет владелец курсов.

## Обоснование

Три уровня и флаги точно выражают банковскую иерархию и позволяют отделению
работать автономно. Разделение `validity` и `daily_required` оставляет
администратору независимое управление формой хранения и требованием на дату
операции. Версионирование сохраняет аудит, не нарушая правило «один действующий
курс на дату». Callback-контракт сохраняет границы модулей.

## Последствия

Положительные:

- единый алгоритм разрешения для API и будущих операций;
- полный журнал установок и понятное авторство;
- права соответствуют ролям и области отделений.

Отрицательные и риски:

- появляются версии в таблице курсов и правила замены;
- контроль курсов при проведении операции ещё не реализован — это следующая
  итерация;
- при смене базовой валюты сохраняется прежнее ограничение по существующим
  курсам.
